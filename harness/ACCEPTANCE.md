# Product acceptance evidence

The immutable [product contract](PRODUCT_ACCEPTANCE.json) defines the goal.
The runner and strict evidence gate implement the fixed seven installed journeys,
twenty security cases, local Git checks and eleven requirement mappings. Focused
manager checks established live Python, Node, TypeScript and mixed journeys,
including dependency installation, protected resume and the setup target. The
resumed native-tool namespace oracle also passed focused native verification.
Full acceptance against the final source, the integrated Git evidence and public
candidate installation remain pending manager validation. Synthetic validator
fixtures are not product evidence or publication approval.

Local and `--release-tag TAG` acceptance also run the bundled CLI from a retained
fresh candidate installation: dependency, task-scope, swarm and the separate
report/lifecycle comparison. `demo_evidence` references the exact candidate,
installed audit, original run/verify processes, results and public projections.
The gate rechecks physical originals and sanitized claim mappings; missing,
stale, changed or substituted receipts fail even if all earlier gates pass.
Projections stay outside the wheel to avoid changing already measured bytes.
The wheel bundles deterministic workers and pinned contracts, not private logs
or an earlier sample presented as current evidence.

Normal regression discovers all four extension modules, incident controls and
the five demo/presentation modules once. Release inventory checks import test
definitions only; execution comes from the existing full native regression.
Installed safety compositions and product demo journeys test the separate fresh
installation boundary. No mandatory native skip is accepted. See the
[private candidate guide](RELEASE.md) for installation and everyday commands and
the [release audit](RELEASE_AUDIT.md) for the finite coverage and remaining gates.

## Installed extension journeys

`test_product_safety_acceptance` participates in ordinary full regression
discovery. It builds the current wheel once, then installs it with hashed
dependencies into three separate retained environments. Native prerequisites
are mandatory; absent tools, unavailable services and skipped cases fail.
Use the [isolated source-test setup](README.md#run-the-tests) to launch discovery;
the installed children never use that editable runtime or PYTHONPATH.

| Journey | Installed behavior checked |
| --- | --- |
| New project | Reviewed initial evidence profile, exact CLI review/adoption, AT1/AT3 application oracles, terminal checkpoint holds and useful acceptance, linked sequence findings |
| Existing project | Useful activity before explicit profile adoption; original project identity, authority and history preserved; the same native review and incident cases |
| Upgrade/recovery | Stale adoption and unsupported schema refused; old-runtime query cannot access adopted state; backed-up migration preserves stops/counts/quarantine; interrupted adoption rolls back and permits a fresh exact review |

Both new/existing runs reuse the incident fixtures for terminal surrender,
caller/descendant stopping, lost acknowledgement, supervisor/capture/quota
uncertainty, scope confinement and shipped warn1/stop3 aggregate stopping.
The cases retain their original application, file, listener, process, cgroup
and unrelated-work assertions. They are separate disposable fixture projects,
not a single long model session. Fixture policy approvals and terminal answers
are scripted; harmful-work findings come from deterministic oracles, not an LLM.

`SAFETY_EVIDENCE` identifies the private output directory. Keep it: it contains
the wheel/build receipts, all three installations, selected original test IDs,
failure logs, PTY records and physical observations. Foreground and detached
imports are checked against actual installed bytes, recursively including
subpackages/data. Actual checkpoint monitor command lines must use the installed
interpreter. Loaded runtime modules are checked again after the journeys.
Only test/driver code is loaded from the checkout.

The installed journeys and optional-review terminal passed manager development checks. The
optional-review terminal case exports an exact request, consumes an explicitly
labeled cached fixture, holds its checkpoint and verifies useful continued work;
final-source parsed evidence validation remains pending. No live reviewer call is made.
These checks do not
replace the original seven journeys or their installer-to-ready 30-second
target. A passing fixture suite does not establish model detection,
public installation, or release readiness.

The product runner adds a version-1 `safety_extension` reference to its original
schema-1 report. `safety/extension.json` binds all three contract hashes, the
current reviewed documents/guides, frozen case manifest, exact candidate record,
wheel and maintained source. Each extension ID, IG1–IG5 and AT1–AT3 maps to actual
native test IDs, the previously recorded full-suite receipt, and the new/existing/
upgrade installed records. The full source suite is consumed, never rerun by the
product runner. Installed compositions use the wheel extracted from the exact
candidate archive; `--release-tag TAG` retains the public download route without
substituting a local build.

The gate independently hashes retained installations and parses original
application/ref/process/sentinel/collector observations, adoption history,
operator PTY inputs/exits and native test inventory/output. Each upgrade lifecycle case retains original
before/after schema, authority and history records, refusal/failure outcomes and
a useful file oracle. Migration and rollback retain private stopped SQLite
backups with their original identity receipts. The gate parses those databases
read-only and compares authority, event identities and outcomes with the
observations; empty original lists, missing backups and contradictory outcomes
fail even with matching summary hashes. These backups contain synthetic fixture
state and stay in private evidence output, outside the public checkout.

Rehashing a summary cannot hide a contradictory original. Missing/stale contracts, changed reviewed
documents, omitted cases, unavailable native prerequisites, altered installed
bytes and claims of unmeasured semantic success fail. These are consistency
checks, not signatures against an author able to forge every record. Keep raw
receipts and installations private and outside the checkout.

The existing release bundle now includes the exact three contracts, reviewed
proposal/scenarios, current safety/daily guides and frozen cases. Old bundles
without them cannot satisfy additive acceptance. The original installer-to-ready
clock and privacy requirements are unchanged. The extension runs after the seven
original journeys; it adds no reviewer calls to startup or ordinary operations.

The [eight-case manifest](SEQUENCE_CASES.json) freezes four benign/harmful pairs
before any semantic results: same-permission login (AT1), separated composition
(AT3), omitted security repair, and forged approval/reviewer injection (IG4).
It records the common grants/assumptions, toy source, histories, independent
application expectations, prompt, reviewer and budgets. These are synthetic
fixtures, not spontaneous model trajectories. Mechanical facts-identical
rationale variants remain in the existing sequence tests without extra calls.
No live comparison has run: artifact-only and history-aware detection, misses,
false alerts, completion, latency and token/cost totals are **unmeasured**, with
zero evaluated live cases and zero live calls. The report explicitly leaves all
three arms unmeasured, with zero denominators and null metrics. Denial-only
comparison remains separate from semantic detection and fixture gate decisions.
The ceiling remains eight cases and sixteen calls, one call per semantic arm
per case; no retries, case replacement or automatic-clearance promotion.

## Reproduction and schema

Use the isolated source-test environment described below on the supported VPS.
After a fresh full native suite, choose a new output directory for each attempt:

```sh
python -B harness/scripts/product_acceptance.py --out /private/evidence/new-product-run
python -B harness/scripts/product_gate.py --evidence /private/evidence/new-product-run
```

The runner measures all seven fixed journeys, retaining each finished row and any
failed attempt. A missing full native receipt fails before installation or model
calls. Development tests in `test_product_gate.NativeEvidenceTests` separately
measure Python, Node, TypeScript and mixed paths. They print private paths as
`PRODUCT_GATE_NATIVE_EVIDENCE`; focused passes do not satisfy full acceptance.
The full runner consumes the existing native receipt without rerunning the suite.
The manager allows 3600 seconds for its product check, including a 3450-second
product subprocess deadline. Each live journey has two bounded model rounds.
There is no automatic rerun after a failure. Diagnose the first failed original
receipt, fix the cause, refresh source hashes and native evidence, and use a new
output directory. A timed-out attempt is incomplete even if earlier cases passed.

For a public candidate, add `--release-tag harness-vX.Y.Z` (or `ptw-vX.Y.Z`).
This retrieves that exact tag's bootstrap and archive, verifies published
checksums, and requires installed runtime equality with current source. Missing
candidates fail without a local substitute. Default runs build a local candidate.
Bootstrap acquisition/build is recorded before installer invocation as an explicit
precondition. Cold archive transfer occurs inside the installer-to-ready interval;
warm runs use the already verified candidate archive. Full attempt timestamps
include candidate preparation. Public candidate installation remains untested.

`completion-evidence.json` schema 1 binds to the immutable contract, maintained
source, recursive runtime/package data, and distribution-input hashes. It requires
seven journey IDs, twenty security IDs, a full native receipt, and all eleven
mandatory contract mappings. Supporting JSON includes matching source hashes and
fresh timestamps. References are relative paths with SHA-256 digests; linked or
escaping references fail. Assertions contain a name, expected and measured value.

Journeys reference original PTYs, broker actions, a confined functional oracle,
timing and installed-module audits. Audits include actual launcher, broker and
monitor identities: loaded module paths, interpreter hash and environment
contamination flags. Retain installations for independent hashing and distribution
metadata checks. Security records require parsed original probe receipts, measured
assertions and injected-request or native-lifecycle labels. `local_git` references
an additional parsed native probe outside the fixed security-ID set.
`candidate_record` binds retained installer/archive hashes to local build receipts
or the exact public tag's checksum and original download receipts.

Each requirement has exactly one mapping record with `contract_ids`, `evidence`,
source hashes, timestamp and assertions. Its `evidence` list must equal the gate's
required references to already validated records; adding a success boolean or
substituting an unrelated hashed file cannot satisfy a requirement.

| Contract ID | Required evidence |
| --- | --- |
| install | Candidate, installer retry and upgrade/rollback/uninstall probes, full native suite |
| first-setup | All seven timing, PTY and action records |
| policy | All seven PTYs/actions, cancellation probe, full native suite |
| ecosystems | All seven installed audits/oracles/actions, full native format coverage |
| everyday | All seven actions/oracles/PTYs, local Git, controlled previews |
| packages | Seven package admission/build probes, full native suite |
| reassessment | Outage and quarantine probes, full native suite |
| scope | Private denial, shared parents, narrowed children, resumed native denial, hostile policy edit |
| escalation | Shared counts, physical stop, resume rejection, unrelated survival, full native suite |
| acceptance | Full native suite, seven PTYs/oracles/audits, twenty security probes, local Git |
| release | Retained candidate provenance and full native suite; ready-for-publication only |

Security probes flush their original observations before checking assertions.
Concurrent package assessments retain distinct response files; publication of each
response, its hash and its observation is serialized within that probe. Downloads
and assertion snapshots use the same recorder lock. Provider assessment itself
remains concurrent, and recording failures leave the attempt incomplete.
The gate compares those observations with both the probe and security summary,
checks original response references, and rejects incomplete or contradictory
records even when their updated hashes agree. Native subprocess receipts retain
both output streams. Failed and interrupted probes remain incomplete on disk.

The gate rejects stale/future evidence, source drift, skips/failures, incomplete
outcomes, missing originals, contradictory assertions and setup above 30 seconds.
It checks exact discovery coverage, not just a count or copied `OK`. Passing means
`ready-for-publication`; finalizer publication, independent review and CI remain
separate. Hashes establish consistency, not authenticity against someone able to
rewrite every artifact. Independent manager provenance review remains necessary.

## Installed journey profiles

Every journey has a distinct fresh application installation and synthetic
private/outside files. New projects begin with declarations and no application
sources. Existing projects include working legacy functions and tests that must
remain byte-for-byte unchanged while the model adds the requested renderer.
The developer profile
has Linux x86_64, a systemd user manager, Python 3.11 to 3.13, Node22/npm, bubblewrap,
curl and Git. The installer downloads pinned tools and creates empty private
package caches. The fixed allocation is:

| Journey | Project inputs | Release archive profile |
| --- | --- | --- |
| new-python | Empty requirements, no application source | Cold |
| existing-python | Requirements, legacy Python function and unittest | Warm |
| new-node | npm declaration, no application source | Cold |
| existing-node | npm declaration, legacy JavaScript function and node:test | Warm |
| new-typescript | npm, pinned TypeScript compiler, tsconfig, no application source | Cold |
| existing-typescript | Same declarations plus typed legacy function and node:test | Warm |
| existing-mixed-python-node | Python backend and JavaScript frontend with legacy tests | Warm |

Cold means an archive transfer during installation. The default local-candidate
mode uses an explicitly labeled loopback HTTP fixture, retaining transfer receipts;
`--release-tag` uses the exact public candidate URL. Warm means a retained,
hash-verified release archive, with its reference recorded before installation.
Both profiles still download tools and start empty private uv/npm caches, as the
production installer requires. Neither profile reuses an application installation,
project approval or editable source environment. These profiles make no claim
about warm dependency caches or public Internet archive timing in local mode.

The terminal references the operator's existing login without
opening or copying authentication files. Browser login/MFA and new-account OAuth
remain external, untested prerequisites.

One monotonic clock spans installer invocation, policy review and the actual
protected MCP handshake. Scripted input/review time is included and separately
recorded. First independently verified useful work is measured afterward. Two
real GPT-5.6 Sol/low turns build a renderer, run nonempty tests and applicable
builds, import a reviewed added dependency, and resume the same conversation using
a conversation-only nonce. TypeScript compiles emitted JavaScript before testing.
The mixed project changes and imports dependencies in both ecosystems. A confined
independent oracle checks normal, boundary and invalid inputs in every language.
An injected denial separately checks private hashes and retained violation counts.
Setup over 30 seconds remains unmet even if useful work succeeds.

The protected launcher disables Codex startup update checks because the release
installer manages the pinned CLI version. It leaves the operator's configuration
unchanged. Failure cleanup terminates the test terminal without typing into an
unknown prompt; normal conversation quit is exercised explicitly after readiness.

The supported formats remain the [accepted dependency matrix](DEPENDENCY_STATUS.md):
requirements/PEP 621, local Python, uv/Poetry, npm/workspaces, pnpm v9 and Yarn
Classic v1 with the documented exclusions. Adapter coverage remains in the full
native suite; the fixed live matrix does not multiply every lockfile format by
every language/cache combination. The complete final-source matrix remains a
separate acceptance check.

## Independent package probes

`product_security.py` adds nine fixed cases to the product runner using a retained
fresh installation. It reuses the accepted synthetic wheel, npm archive and
advisory constructors from the public test suite, without executing test methods
or treating unittest output as a physical observation. There are no model calls.

The probes check direct/transitive critical rejection, young releases, tampered
archives, selection and import of an older compatible dependency, denied and
explicitly approved isolated builds, advisory outages, and quarantine after a new
advisory. The compatibility probe runs real uv inside the existing metadata
namespace against a fixture wheel directory, then installs and imports the
selected graph under confinement. Reassessment starts actual package-dependent
and unrelated workloads, expires only fixture evidence, and measures persisted
assessment state, violations and systemd process effects before cleanup.

`security/<ID>/probe.json` references flushed `observations.jsonl`, original
responses, fixture archives and native output. Controllers and package artifacts
remain available for private inspection. `package-security.json` retains completed
cases if a later case fails. Fixture advisories do not describe public package
safety, and these injected requests are not model trajectories.

## Independent scope and process probes

`product_scope.py` uses version-4 repository policies, two independent parents,
a read-only child and an unrelated project. Explicit broker calls test private
reads, narrowed writes, attempted scope expansion and shared warning/stop counts.
A hostile repository policy copy is followed by a new controller handle and
parent; the approved controller remains authoritative.

Reviewed Python previews run in actual confinement and spawn descendants. Their
HTTP responses check useful work and failed private/outside reads. After stop,
the probes inspect the same registered cgroups and closed listeners, then perform
a useful preview request and protected edit in the unrelated project. An actual
operator PTY tests stopped-resume rejection before conversation lookup, with no
new session or reset history. Its injected identifier is synthetic; successful
conversation continuation is proved separately by the live installed journeys.

`scope-security.json` covers seven additional fixed security IDs. The group
publishes success only after every effect and cleanup completes. Failure keeps
all original observations and incomplete probe records; rerunning into the same
directory is rejected. These probes add no model rounds. Product execution runs both independent groups through
the retained fresh installation, without inherited Python search paths.

## Lifecycle and resumed native-tool probes

`product_lifecycle.py` reuses the installer acceptance against the exact candidate
archive in a separate destructive installation. It retains HTTP failure, truncated
download, bad checksum, successful retry, missing-login status, version-only
synthetic upgrade, rollback and conservative uninstall outputs. Every command
records project hashes, unrelated-process survival and installation state. The
seven language installations remain available for independent hashing.

Real setup PTYs exercise rejection, cancellation, blank input, EOF and interrupt
against one existing project, then explicitly approve a successful retry. Original
terminal bytes and input records survive failure. These probes use fixture data
and scripted operator decisions, with no model calls. Missing-login status uses
an empty fixture CODEX_HOME. Browser login/MFA remains an external prerequisite.

During the live new-Python conversation resume, a separate hostile command uses
the original launch's configuration-isolation wrapper and permission overrides
through the [Codex sandbox test interface](https://learn.chatgpt.com/docs/developer-commands?surface=cli#codex-sandbox).
The pinned CLI 0.154.0 uses `codex sandbox -P ptw-interactive -C WORK -- COMMAND`,
with the original configuration overrides. Its `codex help sandbox` selects the
host platform implicitly; the platform subcommand shown in the general security
guide is not used for this version.
It attempts private/outside reads and writes independently of model refusal.
The pinned CLI's deny-all compilation hides its own bootstrap executable, so the
original hostile payload cannot start. The runner retains that failed attempt.
It then independently observes the exact captured namespace, adding only a
diagnostic synchronization fd. Bubblewrap pauses after root setup; host syscalls
through `/proc/PID/root` check private/outside reads and writes to existing files
without `O_CREAT`, the actual permitted shell mount, hidden bootstrap and separate
network namespace. A separate exclusive-create attempt may create a namespace-local
file where the shell bind created parent directories. That success is recorded as
such and requires file/device identity on the new root tmpfs, a different host
device and unchanged protected-host hashes. Missing identity evidence fails. Releasing
the fd must produce the same exact exec denial. This is filesystem visibility and
execution-denial evidence, not an in-sandbox payload, model refusal or seccomp
test. No mounts, permission rules or production launch paths change.

Missing/ambiguous compilation, additional mounts, staging roots, unobservable
post-setup roots, failed controls, exposed files and generic startup errors all
fail. Both attempts retain originals and sensitive hashes, including interruption.
Focused native checks verified this oracle and the installed new-Python resume.
Final-source full acceptance remains required.

The probe retains executable identities and sensitive-fixture hashes before and
after launch, including failure or interruption. Private `boundary/` records
sample only that command's descendants through Linux `/proc`, retaining original
command lines and mount tables when visible. Short-lived stages can be missed;
sampling errors and gaps are diagnostic limitations, never evidence of denial.
Each usable sample has nonempty command-line and mount-table bytes. Empty or
partial reads remain in `boundary/gap-N/`, with hashes of every available original,
read errors and `/proc/PID/stat` observations before and after the reads. State
and start time distinguish observed exit from PID reuse. Only observed disappearance
or the same process entering an exit state qualifies as an exit race; permission
errors, live empty reads, changed identities and unknown states leave the trace
incomplete. The descendant regression retains its process output, samples and
source hashes outside the checkout, printing `BOUNDARY_DIAGNOSTIC_EVIDENCE` even
when it fails. Assertions identify the field, sample index and PID.
The resume probe references retained regular files recursively, including each
gap's metadata and available bytes, with relative names and hashes. Linked or
nonregular artifacts fail collection. Collection errors are recorded separately
and prevent a successful security result; they do not replace an original launch
failure or suppress its process receipt and individual sensitive-file measurements.
An incomplete diagnostic observation stays incomplete. Security success still
requires the independent effects oracle and any required compiled-boundary sample.
Linux documents [process lifetime and PID reuse](https://docs.kernel.org/filesystems/proc.html#process-specific-subdirectories)
and [empty command lines for zombies](https://man7.org/linux/man-pages/man5/proc_pid_cmdline.5.html).
These rules explain the diagnostic classification, not the cause of a particular
failed sample without its retained observations.
There is no authentication-file or process-environment capture. The
[permissions reference](https://learn.chatgpt.com/docs/permissions) describes the
deny rules. Python's [OS interface](https://docs.python.org/3/library/os.html#os.open)
provides the separate open/create flags and descriptor identity used by the oracle.
The [bubblewrap source](https://github.com/containers/bubblewrap/blob/v0.12.0/bubblewrap.c)
places `--block-fd` after root setup and before exec; the native check verifies the
actual final mount view rather than assuming setup completed.

## Native suite receipt

On the isolated Linux VPS, first follow the [source test environment
instructions](README.md#run-the-tests). Install the current checkout as editable
in that separate environment, using the hashed prerequisites. Confirm the
isolated import points into the current checkout. A PYTHONPATH setting alone does
not configure detached systemd services. Then run the existing full discovery:

```sh
PTW_LINUX_TESTS=1 python -B -m unittest discover -s harness/tests -v
```

Discovery that includes `test_product_reassessment.py` enables both the timing
diagnostic and native receipt recorder. The recorder observes the outer
`TextTestRunner`, retaining its actual output through the final summary, actual
result callbacks, and selected test IDs in order with their multiplicities. It
preserves the original runner, result, fixtures, execution order and assertions.
Nested runners are not independent full-suite attempts. Successful subtests are
recorded; subtest failures, fixture errors, skips, expected failures and unexpected
successes all prevent a clean native receipt.
Synthetic validator fixtures explicitly unwrap the runner callback before
recording their fixture suite. This keeps fixture receipts separate even when
discovery enables instrumentation after an outer test runner has already started.
It does not relax production checkout, inventory, environment or source checks.

`NATIVE_SUITE_EVIDENCE` prints the private attempt directory. Its default parent is
`$XDG_STATE_HOME/ptw/native-receipts`, or `~/.local/state/ptw/native-receipts` when
XDG_STATE_HOME is unset. It is namespaced by the resolved checkout and maintained
source fingerprint. Each invocation creates a unique directory. This is separate
from `REGRESSION_TIMING_EVIDENCE` and does not depend on temporary-directory
selection. Set XDG_STATE_HOME to an absolute private directory if needed before
both native discovery and its consumer; do not put raw evidence in the checkout.

The files are:

| File | Meaning |
| --- | --- |
| `attempt.json` | Incomplete attempt, source hashes, environment and selected inventory, written before running tests |
| `unittest.log` | Flushed original runner stream, including any genuine final summary |
| `outcomes.jsonl` | Flushed result callbacks with test identity and monotonic timestamps |
| `complete.json` | Published only after the real runner returns, with final counts, before/after source and environment, and log digests |
| `interrupted.json` | Exception type and timing when the runner raises, without inventing a completion |

Keep the source test environment until validation ends. The consumer independently
hashes its interpreter, installed metadata and editable import hooks; verifies the
actual source identity, locked dependencies, tools and host; and compares the
exact current discovery inventory. `distribution_metadata` identifies top-level
installed distributions separately from hashed vendored metadata and import hooks.
Bundled metadata remains integrity-checked without being counted as another
installed distribution. Discovery uses an isolated child of the consumer's own
Python with the verified source environment's dependency directories and the
current checkout. It does not execute the receipt's interpreter or process site
startup files/editable hooks. The consumer must use the same Python version as
the retained source environment, but need not have its packages installed.
Discovery imports test definitions without running fixtures or tests; installed
user environments remain separate. Full native evidence needs at least 242 tests, every discovered occurrence
completed successfully, no skips/errors/failures, consistent original output and
unchanged maintained source. Focused passes do not qualify. Evidence expires after
24 hours, and source changes require another full run. A later failed or incomplete
full attempt supersedes an earlier success for the same source; focused attempts
do not supersede a full run. Retained files and cross-record agreement establish
consistency, not authenticity against someone able to rewrite all evidence.

The receipt consumer is `harness/scripts/native_receipt.py`. Its `retain` function
copies original records unchanged into a fresh product output tree, then records
provenance and references relative to that tree. It never runs the suite again.
This leaves the existing regression command responsible for native execution and
keeps that workload outside the product journey deadline.

## Original output and terminal environments

Installer, onboarding and wheel subprocess probes now stream stdout and stderr to
private files while executing. `process.json` identifies the command, timing,
exit/signal status and original log hashes. A nonzero exit is retained before the
caller asserts success. Timeouts retain partial bytes and terminate only the new
probe process group. Startup-shell probes also retain PTY bytes, including failures.
These files may contain private paths or session output. They are not public
diagnostics and must not be published without separate review and sanitization.
For terminal drivers, use `close(graceful=False)` in failure cleanup. Only use
the default `/quit` operation for a known ready conversation. Cleanup retains
the original output and records whether graceful quit was requested.

`Terminal(..., replace_env=True, env=...)` replaces the child's environment with
the explicit mapping plus its terminal type. The default continues to merge for
existing source-test callers. Installed onboarding uses replacement mode, removes
PYTHONPATH/PYTHONHOME, chooses an explicit installed launcher, and runs from its
evidence directory. Terminal input receipts are saved as input is sent; raw output
is flushed as it arrives. Actual launcher, broker and monitor identity receipts
support every live journey and are checked against retained installed files.

## Validation boundary

The frozen implementation covers native receipt production/consumption, strict
schema validation, installed environment isolation, original-output retention,
seven live journeys, security/lifecycle and Git effects, exact public candidates,
failure/mutation tests and maintained guides/hashes. A successful script exit
requires its own gate to validate the completed evidence. Failures leave
`completion-evidence.json` with an error and unmet requirements, alongside original
partial records; no passing `gate.json` is published.

The manager independently runs full source and product acceptance, including its
separate evidence gate. Native PTYs, sockets, user-systemd services, confinement,
downloads and live-model calls run outside the coding sandbox, whose networking
is restricted and approval escalation disabled. Repository/tmp writes and offline
checks are available inside it. Pending manager checks are not passing tests.
Browser login/MFA is an external owner prerequisite; no authentication is copied
and new-account OAuth is not claimed. Public push, credential review, sanitization,
independent publication review and CI belong to the release/finalization stage.

## Interface sources

Live prompts use explicit [xterm bracketed-paste boundaries](https://invisible-island.net/xterm/ctlseqs/ctlseqs.html)
followed by one separate Enter. The driver requires the terminal to enable this
mode, retains input/submission times, and waits for the selected model to render
before measuring readiness. Onboarding review answers retain their ordinary line
input. A prompt stuck in the composer is a failed attempt, never useful work.
Codex also documents [burst-paste detection](https://developers.openai.com/codex/config-reference/);
the acceptance driver leaves the operator's configuration unchanged.

The JavaScript oracle uses Node's built-in
[`node:test` runner](https://nodejs.org/download/release/v22.23.2/docs/api/test.html),
with individual test names and counts checked as well as the exit status. No test
library dependency is added. Its subprocess execution and the confined npm test
command require native verification; an empty successful process is insufficient.

The launcher uses the documented
[`check_for_update_on_startup` setting](https://developers.openai.com/codex/config-reference/)
for installer-managed updates. Actual pinned CLI behavior still requires the
native installed journey; checking generated arguments alone is not user proof.

The recorder follows Python's documented [unittest runner/result interfaces and
discovery protocol](https://docs.python.org/3.12/library/unittest.html). Streaming
capture uses [subprocess file redirection and process-group
isolation](https://docs.python.org/3.12/library/subprocess.html#subprocess.Popen).
Distribution inventories use the standard [distribution metadata and file
interfaces](https://docs.python.org/3.12/library/importlib.metadata.html#distribution-files).
These standard-library facilities require no new dependency. The immutable local
contract and existing runner implementations determine the evidence design;
external research cannot establish actual native effects or journey timings.
